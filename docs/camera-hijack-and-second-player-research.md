# Camera-hijack fix & second-local-player feasibility — research log

Dated investigation log (2026-08-30), not a living reference — see
`docs/placement-lessons.md` for the actionable summary and current state.
This doc captures the full findings from two parallel deep-research
passes done while the game was running but no rebuild was possible, plus
one independent finding of my own, so the next session doesn't have to
re-derive any of this.

## Where things stood going in

`world.connectConveyor` drives the real player's BuildGun to place belts,
which requires forcing the player controller's rotation every poll tick
to get deterministic routing (`AutoRouteSpline` empirically depends on
it) — this is the actual camera hijack. An attempt to fix it by spawning
a throwaway decoy pawn+controller (`AAIController` or `APlayerController`)
as the construction instigator instead, via the real, public
`AFGHologram::SpawnHologramFromRecipe()`, got the hologram permanently
stuck on a `UFGCDInitializing` disqualifier that never clears — tried
across both controller classes, `SetActorTickEnabled(true)`, and
continuous `UpdateHologramPlacement()` reassertion, none worked. See
`docs/placement-lessons.md`'s "ONGOING: camera-hijack..." section for the
blow-by-blow of what was tried live.

## Finding 0 (own research): SML has a real native-function hooking system

`Mods\SML\Source\SML\Private\Patching\NativeHookManager.cpp` is
genuinely implemented (confirmed: no "automatically generated" banner,
real logic), backed by the real `funchook` binary-patching library.
Macros `SUBSCRIBE_METHOD` / `SUBSCRIBE_METHOD_AFTER` /
`SUBSCRIBE_METHOD_VIRTUAL(_AFTER)` /
`SUBSCRIBE_METHOD_EXPLICIT(_VIRTUAL)(_AFTER)` (declared in
`Mods\SML\Source\SML\Public\Patching\NativeHookManager.h:577-620`) let
you hook a REAL compiled FactoryGame function — even one whose `.cpp` in
this SDK is a stub — and get a callback with the real arguments/state
before or after every real call, live, in a running game. AIMod does not
use this system yet (checked, zero `SUBSCRIBE_METHOD` usages anywhere in
`Mods/`).

**This is the single most valuable tool for actually resolving the
"Initializing" mystery** — both research agents below independently hit
the same wall (the deciding logic is 100% stub source, unreadable no
matter how carefully you search), which static research cannot get past.
Hooking the WORKING "RealCharacter" path's `UFGBuildGunStateBuild::
SpawnHologram()`/`InternalSpawnHologram()`/`BeginState_Implementation()`
(or a hookable public/virtual entry point higher up if those turn out to
be non-virtual/inaccessible — `UpdateHologramPlacement()` is confirmed
public and virtual) during a real, successful belt construction, and
logging everything, would give empirical ground truth instead of more
inference. Caveat: `AutoRouteSpline` itself is `private` and its
virtuality wasn't confirmed — may need `SUBSCRIBE_METHOD_EXPLICIT`-style
handling or a different, accessible hook point if it can't be hooked
directly.

## Finding set A: BuildGun hologram construction lifecycle (Explore agent)

**Confirmed, not inferred**: every `.cpp` file that could plausibly
contain the actual `UFGCDInitializing` add/remove logic is a
100%-generated stub — `FGHologram.cpp`, `FGBuildGunBuild.cpp`,
`FGBuildGun.cpp`, `FGCharacterPlayer.cpp`, `FGConveyorBeltHologram.cpp`,
`FGSplineHologram.cpp`, `FGBuildableHologram.cpp`,
`FGBuildableSubsystem.cpp` — all confirmed via the literal "automatically
generated by the Unreal Header Implementation tool" banner, not assumed.
Grepping the entire `Source` tree for `UFGCDInitializing` finds only its
own class declaration (`FGConstructDisqualifier.h:49-57`) — no add, no
remove, no check, anywhere in readable source. **The mechanism does not
exist in this SDK at all; it's compiled entirely into the shipped
binary.**

Despite that, real structural evidence was found for what likely
*differs* between the two paths:

- `UFGBuildGunStateBuild` (`FGBuildGunBuild.h`) has its own
  `SpawnHologram()`/`InternalSpawnHologram()` (private, lines 332, 340) —
  a **distinct wrapper** around the same raw spawn `SpawnHologramFromRecipe`
  does. The wrapper's existence at all is evidence of extra, state-specific
  setup happening after the raw spawn — body is stub, so what exactly is
  unreadable.
- The state has clearance-detector overlap delegate handlers
  (`OnClearanceDetectorAdded`, `BeginClearanceDetectorOverlap`,
  `EndClearanceDetectorOverlap` — lines 266, 344-348) that exist **only
  on the state, not on `AFGHologram` itself** — a genuine example of
  state-exclusive wiring a bare `SpawnHologramFromRecipe()` call
  structurally cannot receive. Caveat: might only be for visualizing
  *other* buildings' clearance boxes, not the hologram's own — unconfirmed
  either way.
- `AFGHologram` has **no `Tick()` override at all** (grepped, absent) —
  consistent with the observed symptom (permanently stuck, not slowly
  resolving) and explains why `SetActorTickEnabled(true)` did nothing:
  clearance/placement checks are event/delegate-driven, not tick-driven.
- `FindPackageMapForPlayerController(const APlayerController*)` (static,
  line 269) hints hologram/construction-message plumbing may depend on a
  real `NetConnection`/`PackageMap` that only a properly-joined player has
  — a bare `SpawnActor<APlayerController>()` never goes through
  login/travel and has neither. Speculative, not proven.
- `mConstructionInstigator` gets set correctly by both paths (real:
  implicitly via the state's spawn call passing Character; decoy:
  explicitly via `SpawnHologramFromRecipe`'s `hologramInstigator` param)
  — so instigator identity alone doesn't obviously explain the gap.

**Ranked next steps from this agent** (already-failed things excluded):
1. Keep the real BuildGun flow but swap identity more surgically — e.g.
   temporarily swap Character's *possessing controller* to a decoy rather
   than spawning an entirely separate decoy pawn, so `HotKeyRecipe`/
   `GetBuildGun`/`GetBuildGunStateFor` all still run for real. **My own
   assessment, added after reading this**: this is riskier than the agent
   frames it — UnPossessing the real Character from the real
   PlayerController mid-session could leave the local viewport with no
   valid view target (black screen, spectator fallback, or worse) since
   that PlayerController IS what's rendering the local screen. Don't
   attempt without a clear, tested rollback and probably a save first.
2. Try passing a non-null `preSpawnFunction` to `SpawnHologramFromRecipe`
   (currently `nullptr` in the current code) — the one explicit "configure
   before BeginPlay" hook the API exposes that's never been exercised.
   Unknown what to configure there without more evidence, but cheap to
   experiment with.
3. Try the untried `hologramOwner`/`hologramInstigator` split: owner=
   Character, instigator=Decoy was tested early and showed the camera
   jolt; owner=Decoy, instigator=Decoy is the current (stuck) code. The
   reverse combination (owner=Decoy, instigator=Character) was never
   tried — low priority, since instigator=Character defeats the point
   (real Character's inventory/identity gets reinvolved).
4. **Best evidence-backed option**: a genuine second local player (see
   Finding set B) — this agent independently arrived at the same
   recommendation as the sibling research task, from a different angle
   (real `NetConnection`/`PackageMap` plumbing hints).
5. Live-diagnostic, not source-reading: log the hologram's clearance
   detector's overlap state every poll tick on both the working and
   broken paths to directly confirm/deny the clearance-delegate
   hypothesis above, without needing to read the stub logic at all.

## Finding set B: second-local-player feasibility (Explore agent)

**Confirmed from real, non-stub Unreal Engine source** (not FactoryGame —
this part of the investigation is on much firmer ground):

- `UGameInstance::CreateLocalPlayer()` (`GameInstance.cpp:835-930`, real
  engine source) is small and well-behaved: checks a splitscreen player
  cap (4, plenty of headroom), creates a new `ULocalPlayer`, and — if
  `bSpawnPlayerController=true` and the world isn't `NM_Client` (true for
  single-player) — calls `SpawnPlayActor()`, which drives `AGameModeBase::
  Login`→`PostLogin`, **the exact same sanctioned path a real
  multiplayer client join uses**. You would not be hand-rolling a join
  flow; calling this one engine function *is* the join flow, and it
  would route through `AFGGameMode`'s own (stub-hidden, but presumably
  standard) `Login`/`PostLogin`/`RestartPlayer` with
  `DefaultPawnClass = AFGCharacterPlayer::StaticClass()` (confirmed real
  default from `FGGameMode.cpp`'s constructor).
- **Headless (no visible second viewport) is a real, confirmed, built-in
  capability**, not a hope: `UGameViewportClient::SetForceDisableSplitscreen(true)`
  (`GameViewportClient.h:421`) forces every extra local player's viewport
  rect to zero size, and `ULocalPlayer::CalcSceneViewInitOptions`
  (`LocalPlayer.cpp:742,749`) explicitly bails out and renders nothing for
  a zero-size viewport. One line, revocable, no split-screen ever appears.
- **Cleanup is real and clean**: `UGameInstance::RemoveLocalPlayer()`
  (`GameInstance.cpp:958-1022`) destroys the `PlayerController` and
  unregisters the `ULocalPlayer` — a genuine, engine-native teardown path,
  confirming this can be temporary/controlled rather than permanent.
- **Input isolation is achievable via two independent, real mechanisms**:
  standard engine input routing is keyed to a specific local-player
  index/`FPlatformUserId` (a second local player given no real device
  mapping structurally cannot receive real input), AND FactoryGame
  appears to have its own `FSlateSingleUserInputMapping` (`FGGameInstance.h:24-39`,
  real class declaration, hardcodes every input accessor to user index 0)
  as a second safety net — though where it's actually installed is
  stub-hidden, so its live effect isn't 100% certain. AIMod's own ~30
  existing call sites all hardcode `GetPlayerPawn(World, 0)`, so nothing
  already written would accidentally start operating on a second player
  (index 1) by mistake.
- **Real, confirmed Central Storage/inventory bridging APIs already exist
  in FactoryGame** — exactly matching what would be needed to stock a
  second character's inventory without giving it its own separate supply:
  `UFGInventoryLibrary::GrabItemsFromInventoryAndCentralStorage(...)`
  (`FGInventoryLibrary.h:180-181`, doc: "Removes the number of items...
  from the inventory component AND the central storage subsystem"),
  `GrabItemFromCentralStorage`/`MoveItemFromCentralStorage` (192, 202),
  and the exact real per-player preference (`AFGPlayerState::
  mTakeFromInventoryBeforeCentralStorage`, `FGPlayerState.h:1023`) behind
  the real player's own "auto-restock from Depot" feature the user
  mentioned already exists. This is the SAME underlying subsystem
  (`AFGCentralStorageSubsystem`) AIMod's own `WithdrawFromCentralStorage`
  RPC already uses (`AIModFunctionLibrary.cpp:5153-5222`) — no new
  bridging code needed, just reuse of a proven pattern: top off the
  second character's own `UFGInventoryComponent` from Central Storage
  before each construction call, then let normal affordability checks run
  against that now-stocked inventory. No evidence the hologram's own
  `CheckCanAfford` talks to Central Storage directly — the bridge has to
  be "top off inventory first," not "make affordability check the Depot."

**Real risks flagged, not confirmed either way**:
- Save-game orphaning: `AFGCharacterPlayer`/`AFGPlayerState` both
  implement real (non-trivial, stub-hidden) `ShouldSave_Implementation()`
  — if the second player isn't cleanly removed via `RemoveLocalPlayer()`
  before a save, it's plausible (not confirmed) it gets serialized and
  reloads as an orphaned actor. Needs a live save/load test to settle.
- A second, real `AFGCharacterPlayer` means a second, VISIBLE humanoid
  character model in the world — inherent to this approach, not a bug,
  but a real behavior change worth being upfront about (this is also
  presumably the point, for the "autonomous embodied second player" half
  of the user's interest, separate from just fixing the camera hijack).
- Performance cost of a second full character (mesh/anim/inventory/full
  equipment stack) vs. the much lighter bare decoy pawn — not quantified.
- HUD/achievement singleton risk — no evidence found in the readable
  portions of source, but can't be ruled out given how much is stub.

**Recommended smallest safe next experiment** (this agent's own
conclusion, well-reasoned): call `CreateLocalPlayer()` +
`SetForceDisableSplitscreen(true)`, log whether a real second
`AFGCharacterPlayer` actually gets spawned/possessed cleanly with zero
visible viewport impact — settle that risk FIRST, cheaply — then, only
if that works cleanly, feed that second character's real, locally-owned
PlayerController into the EXISTING `"PlayerController"` instigator
strategy branch already scaffolded in `ConstructConveyorBelt` and see
empirically whether a REAL local player (not a bare decoy) finally clears
`UFGCDInitializing`. That single live test directly answers the question
neither research pass could answer from source — and it's incremental,
reusing code that already exists rather than requiring a new strategy.

## Bottom line for next session

1. `"RealCharacter"` remains the only working `instigatorStrategy` —
   no regression, camera hijack unsolved.

2. **`"LocalPlayer"` was live-tested 2026-08-30 and is CONFIRMED BROKEN —
   DO NOT USE without fixing this first.** `CreateLocalPlayer()` itself
   worked exactly as the research predicted (log confirms: `"spawned
   real second local player, pawn class=Char_Player_C"`, no errors) and
   the hologram STILL got stuck on `UFGCDInitializing` (same as every
   other strategy) - so the experiment's original question was answered
   cleanly (genuine local-player identity is NOT the missing ingredient
   either, ruling out a 5th hypothesis). **But the `RemoveLocalPlayer()`
   cleanup call had a real, serious side effect on the REAL player**: the
   real player's screen got stuck on Satisfactory's death/respawn loading
   screen (`"INITIALIZING RESPAWN_SEQUENCE.BAT..."`) and it never
   dismissed - confirmed by the user as a genuine, permanently-stuck
   overlay (game underneath kept simulating normally the whole time -
   input produced sound/action feedback, `world.player` RPC kept
   returning a valid, UNCHANGED position throughout - but the loading
   screen widget itself never went away, even after Escape/Alt-Tab).
   **Required a full game restart to clear.** Log evidence at the exact
   same timestamp as the cleanup: `PIE: Error: CreateWidget cannot be
   used on Player Controller with no attached player.
   BP_PlayerController_C_... has no Player attached.` - strongly suggests
   the second player's teardown triggered some UI/respawn-flow widget
   creation that got bound to the wrong (already-removed) player and
   never received its completion signal. Real player's in-game position
   was unchanged before/after (not a true relocate-on-death), so this
   may not even be a genuine "your character died" event as much as a
   respawn-flow widget getting triggered and stuck in isolation - either
   way, it's a real, confirmed, session-breaking bug in the current
   `"LocalPlayer"` implementation, not a hypothetical risk anymore.
   **Do not re-test this strategy until the CreateWidget/no-attached-
   player issue is understood and fixed** - likely needs the widget/UI
   side of `RemoveLocalPlayer`'s interaction with FactoryGame's
   respawn-screen Blueprint investigated (possibly via SML's native
   hooking, Finding 0) before trying again, and probably needs the
   second player's teardown ordered/sequenced differently (e.g.
   explicitly ensure no UI system still references the second
   PlayerController before calling `RemoveLocalPlayer`).

3. Since all five real-vs-decoy identity hypotheses are now exhausted
   (AIController, PlayerController, SetActorTickEnabled, continuous
   UpdateHologramPlacement, genuine LocalPlayer) and the LocalPlayer path
   specifically introduced a new, worse problem, **SML's native hooking
   system (Finding 0) is now the clearly-preferred next step** over
   trying yet another instigator-identity variant - instrument the
   WORKING "RealCharacter" path live and get empirical ground truth on
   what `UFGCDInitializing` actually needs, rather than continuing to
   guess at identity-based fixes.
4. `ConstructBuildingAtPosition`'s own, separate camera-rotation issue
   (buildings, not belts — confirmed to exist, live-tested this session)
   has not been investigated at all yet.
