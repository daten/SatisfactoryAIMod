# FactoryGame is a precompiled binary, not built from the stub source

Recorded 2026-08-24. This corrects/refines a caveat repeated across
[resource-node-research.md](resource-node-research.md),
[buildable-research.md](buildable-research.md), and
[building-placement-research.md](building-placement-research.md): those
docs note that `Source/FactoryGame/Private/*.cpp` files are auto-generated
stubs ("This file has been automatically generated by the Unreal Header
Implementation tool", bodies like `return nullptr;`). That's true, but the
implication drawn from it needs a correction — **the actual compiled
`UnrealEditor-FactoryGame.dll` that the Editor and packaged game load is
NOT built from these stub files.** It's a precompiled binary Coffee Stain
ships as part of the modding SDK.

## Evidence

- 842 of 971 `.cpp` files under `Source/FactoryGame/Private/` (87%) carry
  the auto-generated-stub marker (confirmed via
  `grep -rl "automatically generated" Source/FactoryGame/Private | wc -l`).
- `Binaries/Win64/UnrealEditor-FactoryGame.dll` exists (23.5MB, plus a
  248MB `.pdb`) and is dated *before* this session's build activity
  started.
- **UBT has never compiled `FactoryGame` (or `FactoryEditor`,
  `FactoryPreEarlyLoadingScreen`, etc.) from source in this environment
  for the `FactoryEditor`/`Development` target.** Checked directly:
  `Intermediate/Build/Win64/x64/FactoryEditor/Development/` contains
  intermediate directories only for `Core`, `CoreUObject`, `Engine`,
  `Slate`, `UnrealEd` — base **engine** modules — with no `FactoryGame`,
  `FactoryEditor`, or `DummyHeaders` subdirectory at all. Zero `.obj`
  files exist anywhere for `FactoryGame` under this target.
- By contrast, `DocMod` and `SML` (the actual modder-authored plugin
  content under `Mods/`) *do* have full intermediate build trees with
  real `.obj` files for every source file, confirming UBT genuinely
  compiles those from source on every `tools/build-editor.ps1` run — the
  normal incremental-build behavior.
- `DummyHeaders` (`Source/DummyHeaders/`) *does* have compiled `.obj`
  output, but only under `Shipping`/`FactoryGameSteam` intermediate paths
  (likely produced once, at SDK-build time by Coffee Stain, not by this
  session) — not under the `FactoryEditor`/`Development` tree either.

## What this means

The header declarations under `Source/FactoryGame/Public/` are a
faithful description of the **real, currently-installed game version's**
API surface (matches CLAUDE.md's "installed headers are especially
important because documentation can lag behind the currently installed
game/SML version"). The `.cpp` stub bodies are placeholders that exist
only so UBT can generate a linkable module shape for compiling DocMod/SML
against — they are never actually what runs. **The real implementation
Coffee Stain wrote is what's loaded at runtime**, in the precompiled
`UnrealEditor-FactoryGame.dll`.

Practically:

- Claims in prior research docs like "whether `AFGBuildableSubsystem` is
  actually populated at runtime is unverified from source" remain
  literally true (source can't prove it either way) — but the *actual
  runtime behavior*, once observed, reflects Coffee Stain's real,
  production implementation, not a broken stub. There is no reason to
  expect resource node purity, buildable enumeration via
  `TActorIterator`, recipe validation, or anything else built so far to
  behave differently than it would in the shipped, unmodified game.
- This is why an in-process self-test (see below) is trustworthy: code
  running inside the actual Editor/PIE/packaged-game process is calling
  into the real compiled game logic, not the stub bodies visible in this
  repo's source tree.
- It also means DocMod cannot "fix" or meaningfully influence
  `FactoryGame`'s own internals by editing `Source/FactoryGame/` — those
  edits would only affect a local recompile that (per the evidence above)
  isn't how the actual running binary gets produced in this environment.
  This isn't a new constraint — CLAUDE.md already forbids modifying
  FactoryGame source — but it's now backed by a concrete mechanical
  reason rather than just a policy rule.

## Why an automated self-test is worth building given this

Since the real FactoryGame implementation is what's actually running,
tests that execute inside a loaded game world (PIE, standalone, or a
packaged build) genuinely exercise production game logic — enumerating
real resource nodes, reading real recipe/production state, etc. This is
why `Mods/GameFeatures/DocMod/Source/DocMod/Private/DocModSelfTest.cpp`
(added alongside this doc) is worth having: its checks are validating
DocMod's code against the real game, not against stub placeholders.
